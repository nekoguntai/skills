# Shared loop run state (schema 1)

The schema tracks loop passes, delivery evidence, artifact preservation, and
cleanup. Workflow profiles retain their own domain predicates. It does not
impose a grade rubric or bug-scrub severity/coverage rules on other loops.
All JSON writes use the helper's sibling lock, monotonic revision, and atomic
replacement. Do not edit a live state file manually.

## Initialize and resume

Resolve the required pr-delivery skill and set `PR_DELIVERY_SKILL_DIR` to its
actual directory for helper invocations. API 1 is required. Resolve all companion
repositories up front. Use a stable pre-existing checkout as `repoRoot`.
Choose a unique state path such as
`~/.codex/state/<workflow>/<repository-name>/<run-id>.json` outside every
checkout, including companion and owned worktrees.

```bash
python3 <pr-delivery-dir>/scripts/loop_state.py init --workflow <workflow> \
  --path <state.json> --run-id <unique-kebab-case-id> \
  --repo-root <stable-absolute-root> --target-branch <branch> \
  --current-sha <full-target-sha> --max-passes 2 \
  [--target-remote <remote-name>] \
  [--companion-repo <stable-companion-root>]
```

`targetRemote` defaults to origin when configured, otherwise the sole remote,
or local refs when there are no remotes. Multiple non-origin remotes require
`--target-remote`. Init and cleanup/decision gates read the actual remote target
SHA (or local target ref in a remote-less repo); a passing inventory check alone
never establishes audit freshness.

Initialization starts iteration 1. Defaults:

| Workflow | Delivery/pass budget | Required observation artifact |
| --- | --- | --- |
| grade-loop | 2 | Grade report and nonempty grade history |
| rationalize-loop | 2 | Convergence plan/report |
| frontend-pr-loop | 2 | Frontend inspection evidence/report |
| visual-consistency-loop | No arbitrary cap; stop when no major visual or navigation findings remain | Visual inventory and audit evidence |
| feature-validation-loop | 1 | Canonical CSV snapshot plus evidence/derived outputs as applicable |
| implement-merge | No arbitrary cap; complete the selected plan | Phase/plan acceptance evidence |
| recursive-plan-review | No arbitrary cap; convergence rule applies | Reviewed plan and disposition evidence |
| scaffold | No arbitrary cap; existing coverage/CI gates apply | Gate/coverage/protection evidence |
| release | No arbitrary cap; requested release gates apply | Requested release gate/artifact evidence |

Set a positive `--max-passes` when the user gives a bounded budget. Null
`maxPasses` records an uncapped workflow; it does not override its stopping rule.
An initially satisfied audit needs no delivery. Bug-scrub uses its own state
helper and termination policy while sharing this inventory library.

Resume by validating and reading the same state path. Never rerun init, replace
the baseline, reset the budget, or switch workflow profile. Reconcile Git/PR/CI
evidence before continuing. Old runs without recorded starting inventories
require trustworthy historical evidence and reviewed migration; never capture
leftover resources as an alleged original baseline.

Nested loops use the outer caller's `state_helper`/`state_path` and ownership,
not this init command. Their scoped cleanup returns exact-resource absence;
the outer owner runs the cleanup gate after all its resources settle.
Strict read-only/no-files work does not initialize state. The delivery and
cleanup contract never authorizes a PR, merge, release, or publication by itself.

## Fields

- Immutable identity: `workflow`, `schemaVersion: 1`, `runId`, `repoRoot`, `targetBranch`, `targetRemote`.
- Controls: immutable positive or null `maxPasses`; `iteration` starts at 1 and advances
  exactly one at a time; `revision` is maintained by the helper.
- Progress: `currentSha`, `status`, `stage`, nullable `reason`.
- Status: `active`, `blocked` (resumable, reason required, retains its current stage and may retain unfinished resources),
  `complete` (workflow acceptance predicate satisfied), or `deferred` (findings remain, reason required).
  Complete/deferred runs are terminal and read-only.
- Stage: `audit`, `planning`, `implementation`, `delivery`, `post-audit`,
  `cleanup`, `complete`. Complete/deferred status requires stage `complete`.
- `cleanup`: immutable `baselines` captured through pr-delivery's inventory
  API and `checks` generated by `verify-cleanup`. Each check records `iteration`,
  `verifiedAt`, and all baseline roots in `repositories`. Baselines identify the
  repositories and the primary checkout assignment and let the gate report
  collaborator changes; they are not an inventory every collaborator must keep.
- Arrays: `resources`, `artifacts`, `audits`, `deliveries`.

Construct a complete candidate from freshly read state. Preserve its revision:

```bash
python3 <pr-delivery-dir>/scripts/loop_state.py validate --path <candidate.json>
python3 <pr-delivery-dir>/scripts/loop_state.py replace \
  --path <state.json> --candidate <candidate.json>
```

`validate` checks document structure, not live Git. `replace` reruns the live
cleanup gate (owned resources absent, primary checkout restored) and archived
evidence before entering cleanup, completing, deferring, or advancing. Planning/implementation transitions also verify the live target
and current (or just-completed prior-pass) audit/archives before consuming them.
For grade, rationalize, frontend, and visual consistency profiles, persist actionable planning
before implementation, then implementation before delivery. Delivery bookkeeping
may record merge/CI results before the post audit; entering further planning or
implementation still requires fresh evidence. Evidence from any delivered pass must be its post audit, including recovery
planning after that pass merged. A prior receipt cannot hide a later owned leftover or archive corruption.

## Resources

```json
{"repoRoot":"/stable/repo","kind":"worktree","identifier":"/owned/pass-1",
 "owner":"grade-run-123","iteration":1,"remote":null,"status":"active"}
```

Kinds are `local-branch`, `remote-branch`, `worktree`. Branch identifiers are short
names; worktree identifiers are absolute paths. Only remote branches name a
configured `remote`; others use null. Owner equals runId. Append `active` entries
before creation (and remote entries before pushing). All fields except status
are immutable. Identity includes repo, kind, remote, identifier. Use distinct
names for each pass. Baseline resources cannot become loop-owned.

Status is `active`, `preserved`, or `cleaned`. Only verified absence justifies
cleaned; it is terminal. A preserved resource can later become cleaned after
safe recovery. No conversion or cross-pass retention is allowed. The helper
checks inventories but never deletes branches, worktrees, or source reports.

## Artifacts and audits

After every report/plan/validation invocation, archive required outputs and
changed evidence. Grade additionally archives the report and changed trend
history files. Archive plans and supporting evidence before their checkout is
removed. Preserve full unique commit history separately when files alone cannot
preserve it. Do not include credentials/private evidence in a public repository.

```bash
python3 <pr-delivery-dir>/scripts/loop_state.py archive \
  --path <state.json> --source <absolute-file> --kind report
```

Kinds are `report`, `history`, `plan`, `evidence`. The helper copies bytes outside
all worktrees and appends an immutable record containing `source`, `archive`,
`sha256`, `iteration`, `kind`. Use the returned archive path in audit records.
An interrupted archive is reconciled by exact bytes, never silently overwritten.

```json
{"iteration":1,"phase":"initial","sourceSha":"<full-target-sha>",
 "report":"/state/run-artifacts/report-file",
 "history":["/state/run-artifacts/history-file"],
 "outcome":"actionable","findings":["Evidence-backed finding identifier"]}
```

Audits are append-only. Phase is `initial` or `post`; outcome is `clean`,
`actionable`, or `deferred`. A clean observation has no remaining selected blockers; other outcomes require
findings. Interpret these outcomes using the calling workflow's original scope
and stopping rule, not a requirement to fix every possible backlog item. References must name archived report/history from the same iteration.
A delivered pass must end with a post audit at `currentSha` before cleanup.
A pre-delivery reinspection is another initial observation in the same iteration.
For non-grade workflows, `report` may reference a `report`, `plan`, or `evidence`
artifact and `history` may be empty. Grade requires a report-kind artifact and
nonempty history. These archive snapshots never replace the canonical CSV,
requested code edits, plan, or published artifact itself.

Planning/implementation phase sequencing applies to grade, rationalize, frontend,
and visual consistency profiles; the other workflows retain their own phase logic.
All profiles verify target freshness, preserved artifacts, ownership, and
cleanup before progression or terminal success.

Before cleaning generated files, run `verify-artifacts --path <state.json>`.
It checks all archives and the most recent archived copy of every still-existing
source file. If the source changed, archive the new version and update audit
references with a new audit record. After this verification, restore only the
exact loop-generated files (preserving archived evidence and unrelated changes)
and perform safe resource cleanup under repository permissions.

## Deliveries

Register each PR before subsequent merge transitions:

```json
{"url":"https://forge/repo/pulls/123","iteration":1,"state":"open",
 "mergeSha":null,"mergeVerified":false,"targetCiSha":null,"targetCiVerified":false}
```

State is `open`, `merged`, or `closed`. Record actual merge ancestry and exact
merge-SHA target CI through pr-delivery. A merged record can gain verification
as CI completes; established SHAs and successful verification cannot be rewritten.
A closed unmerged record is immutable. Record closure/recovery reasons in durable
evidence. Open or unverified merged deliveries block cleanup success.

## Boundaries and exits

1. Archive and verify evidence; settle PRs, agents and owned resources.
2. Run `verify-cleanup --path <state.json>` in the current iteration. It requires
   current audit evidence, settled delivery, intact archives, every owned
   resource verifiably absent, and each primary checkout on its original
   assignment. It prints branches and worktrees other collaborators added or
   removed as `collaborator change` lines; record them in the report and leave
   them alone (see loop-execution.md, "Collaborator-tolerant cleanup gate").
   Then run `loop_state.py stale --repo-root <root>` and settle any of our own
   forgotten resources it lists.
3. Reload state; the helper may have increased revision.
4. For a follow-up, increment iteration by one, set active/audit, clear reason,
   and `replace` before reserving any new resources. The preceding audit must
   be actionable and fresh. If the target SHA changed, refresh audit evidence
   before continuing. If the target is unchanged, consume the prior pass's
   archived audit in Phase 2; a redundant full inspection is not required. A new
   post-delivery audit is still required. The same starting baseline survives
   every pass.
5. For initial-clean or final-clean exits, set complete/complete. For budget
   exhaustion or another deliberate deferral, set deferred/complete and reason.
   Use `replace`, which repeats the live gate. Never claim a deferred run has
   no major findings. If cleanup/evidence is blocked, retain status blocked and
   the current stage and report exact unfinished resources; no success gate is
   bypassed by calling this an exit.
